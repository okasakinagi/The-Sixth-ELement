# 内部：相似度 / 向量 相关 API（Internal APIs）

说明：以下 API 均为内部接口，仅供服务间或后台调用，需要 `Authorization: Bearer <token>` 鉴权。请勿将这些接口暴露给未经授权的第三方。

1. POST `/api/v1/internal/vector/generate-string`
   - 描述：为给定对象（`user` 或 `survey`）生成用于向量化的一段字符串。
   - 输入 JSON：
     - `ref_type`: `"user"` 或 `"survey"`（必填）
     - `ref_id`: 对象 ID（必填）
   - 返回：`{"text": ""}`（当前实现保留空串，TODO：可改为基于题目/用户资料的拼接文本）
   - 备注：此接口当前为占位，返回空字符串以便上层流程保持一致。

2. POST `/api/v1/internal/vector/generate`
   - 描述：为指定对象生成并持久化向量（若已存在则按规则复用）。
   - 输入 JSON：
     - `ref_type`: `"user"` 或 `"survey"`（必填）
     - `ref_id`: 对象 ID（必填）
     - `dim`: 可选，向量维度，默认 100
  - 行为：
    - 对于 `user`：**始终重新计算并覆盖**（即 `generate` 对 `user` 类型会强制重算）。
    - 对于 `survey`：保持原有行为：若已有向量则直接返回（不重算），否则生成并保存。
     - 若无向量：调用内部的文本生成（当前返回空字符串）→ 将文本向量化（当前为确定性 placeholder 向量化）→ 存入 `IDVector` 表（以 float32 二进制存储）→ 返回向量数组。
   - 返回：`{"vector": [float,...]}`

3. POST `/api/v1/internal/similarity/compute`
  - 描述：计算并返回指定 `user_id` 与 `survey_id` 的余弦相似度。
    - 当前实现：**始终重新计算**（不会复用当天已存在的缓存）；计算前会强制为 `user` 与 `survey` 重新生成/刷新向量（`survey` 向量因已存在通常会被复用，除非缺失）。
   - 输入 JSON：`{"user_id":"...","survey_id":"..."}`
   - 返回：`{"cosine": float, "cached": bool}` 或 422/错误信息
   - 返回：`{"cosine": float, "cached": bool}` 或 422/错误信息。注：`cached` 在当前实现中始终为 `false`（因始终重算）。

4. POST `/api/v1/internal/vector/encode`
   - 描述：把给定文本编码为向量并存入 `IDVector`。
   - 输入 JSON：`{"ref_type":"user|survey","ref_id":"...","text":"...","dim":100}`
   - 返回：`{"vector": [float,...]}`
   - 备注：不同于 `/generate`，该接口直接接受任意文本进行编码并持久化。

5. POST `/api/v1/internal/recommend`
   - 描述：为给定 `user_id` 返回若干相似度最高的问卷（内部用于召回/推荐）。
   - 输入 JSON：`{"user_id":"...","num":10}`（`num` 为返回数量）
   - 行为：
     - 从数据库随机抽取 `10 * num` 条问卷（或数据库返回上限），为每个问卷计算与用户的余弦相似度（若已有当天缓存则复用，否则生成问卷向量并计算并持久化相似度）。
     - 将候选按 cosine 降序排序，返回 top `num`。
   - 返回：`{"items": [{"id":"...","title":"...","cosine":float}, ...]}`

安全与性能备注：
- 向量在数据库中以二进制 `float32` 存储（`BinaryField`），读取时会反序列化为浮点数组；当规模或检索需求上升时，建议将向量同步到专用向量库（Milvus / Qdrant / Faiss）并在关系库中只存元数据/外部 id。
- `generate-string` 当前实现返回空字符串；建议改为基于 `Survey.title+description` 或 `AppUser` 的 `nickname+tags` 生成更有意义的文本，以提升向量质量。

**关于“始终为 user 重算”的消耗估算与建议**
- 背景：当前实现中对 `user` 类型的向量生成在 `/vector/generate` 被设计为强制重算；`/similarity/compute` 也会在计算前强制重算 user 与 survey 向量。因此当推荐/计算在同步请求路径（用户触发且实时等待返回）中使用时，会带来额外计算与 IO 开销。

- 粗略消耗估算（示例，量级估计，需按真实部署校准）：
  - 向量维度：100（默认）。生成单个向量（placeholder 实现）约需做 ~100 次浮点操作；真实的深度模型（如 embedding API）每次调用延迟 50-500ms，且有直接成本（API 调用计费）。
  - 推荐一次（`num = 10`）实现逻辑：从 DB 随机抽取 ~100 条候选（当前实现为 `10 * num`），对每条候选保证有向量并计算余弦 → 需做 100 次向量读取/可能的生成与 100 次余弦计算。CPU 开销对单机/低并发可接受，但当并发用户数达到数百至数千时，整体延迟与资源占用会线性放大。若 embedding 使用外部模型，则 100 次 embedding 请求将产生巨大延迟与成本。
  - 存储/IO：向量以二进制 float32 存储在关系型 DB 中，读取 100 个向量（100*100 floats ≈ 40KB）网络/DB IO 并不大，但读取并反序列化仍有成本；高并发下会对 DB 产生明显压力。

- 可能的后果（风险）：
  - 实时计算延迟增大，影响用户体验（页面卡顿、超时）。
  - 数据库与应用服务器负载上升，影响其他业务接口。
  - 当使用付费 embedding 服务时，成本显著增加。

- 缓解与优化方案（建议组合使用）：
 1. 异步/预计算
    - 离线或后台定期为活跃用户预生成向量与相似度（例如夜间/定时任务或在用户活跃时触发异步任务），在实时请求中直接读取缓存结果，避免阻塞请求路径。
 2. 缓存与 TTL
    - 在 `SurveyUserSimilarity` 中引入短 TTL（例如 1 小时或 24 小时）和 `cached` 标志；实时 `compute` 可默认读取缓存，只有在明确需要时（例如用户编辑了标签或手动刷新）才 `force` 重算。
 3. 限制候选数与近似检索
    - 将随机抽样规模从 `10 * num` 调整为更小值（如 `4 * num`）或使用近似最近邻引擎（Faiss/Qdrant/Milvus）来快速召回高质量候选，减少需要比较的向量数量。
 4. 后台批量计算
    - 当用户完成关键行为（提交问卷、修改标签）时，异步触发权重/向量更新，不在用户等待的请求路径中执行。
 5. 可选的 `force` 参数与策略
    - 保留 `force` 标志，但默认不强制实时重算。把强制重算改为显式操作（例如后台手动触发或管理员操作），或限制只对小比例用户/测试用户生效。
 6. 升级向量存储与检索
    - 当规模增长，考虑将向量同步到专用向量库并以 ANN（近似最近邻）实现召回，关系库只保存元数据/映射 ID。
